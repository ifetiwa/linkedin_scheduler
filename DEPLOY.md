# Deploy to Render

This app runs as a single web service on [Render](https://render.com) with:
- Flask dashboard + post-publishing scheduler in one process
- A 1 GB persistent disk for `applied_jobs.json`, `external_applied_jobs.json`, `scheduler_analytics.db`
- A daily cron job that triggers the auto-apply campaign

Total cost on the recommended plan: **~$8/month** (Starter web service + tiny cron).

## 1. Push the repo to GitHub

```bash
git init
git add .
git commit -m "Initial deploy"
git branch -M main
git remote add origin git@github.com:<your-username>/linkedin-scheduler.git
git push -u origin main
```

`.gitignore` already excludes secrets (`.env`), tracker files (`applied_jobs.json`, etc.), and the `.venv`.

## 2. Create the services in Render

1. Sign in to [render.com](https://render.com) → **New +** → **Blueprint**.
2. Connect your GitHub account and pick the repo.
3. Render reads `render.yaml` and previews two services:
   - `linkedin-scheduler` (web)
   - `daily-apply-cron` (cron job)
4. Click **Apply**.

## 3. Set the secret env vars

After the blueprint is applied, Render will prompt for the values marked `sync: false` in `render.yaml`.

For the **`linkedin-scheduler`** service:

| Var | Value |
|---|---|
| `LINKEDIN_ACCESS_TOKEN` | Your LinkedIn access token |
| `LINKEDIN_PERSON_URN`   | `urn:li:person:XXXXXXXX` |
| `CRON_SECRET`           | Auto-generated by Render — copy the value |

For the **`daily-apply-cron`** service:

| Var | Value |
|---|---|
| `DASHBOARD_URL` | The URL Render assigns the web service, e.g. `https://linkedin-scheduler.onrender.com` |
| `CRON_SECRET`   | Same value as on the web service |

## 4. First deploy

The web service builds (`pip install -r requirements.txt`) and starts gunicorn. Watch the logs — you should see:
```
[INFO] Starting gunicorn 23.0.0
[INFO] Listening at: http://0.0.0.0:10000
```

Open the URL Render assigned. The dashboard loads, the scheduler thread is running in-process, and your tracker JSONs are now on the persistent disk at `/var/data/`.

## 5. Verify the cron

Render's cron page shows the next run time. Test it manually: click **Run Now**. Check the cron's logs for:
```
Status: 200 {"applied": 100, "duplicates": 0, "errors": 0, "status": "ok"}
```

## How it all fits together

```
┌────────────────── Render ──────────────────┐
│                                             │
│  ┌─ web service (gunicorn -w 1) ─────────┐  │
│  │  Flask dashboard at /                 │  │
│  │  Daemon thread: schedule.run_pending  │  │
│  │  Persistent disk → /var/data/         │  │
│  │     applied_jobs.json                 │  │
│  │     external_applied_jobs.json        │  │
│  │     scheduler_analytics.db            │  │
│  └───────────────────────────────────────┘  │
│            ▲                                 │
│            │ POST /api/cron/apply-jobs       │
│            │ (CRON_SECRET-gated)             │
│  ┌─ cron (daily 13:00 UTC) ──────────────┐  │
│  │  curl … the dashboard endpoint        │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

## Local development

Local dev still works exactly as before:
```bash
python -m venv .venv
.venv\Scripts\Activate.ps1   # Windows
pip install -r requirements.txt
copy .env.example .env       # then fill in values
python app.py                # http://localhost:5000
```

Leave `ENABLE_SCHEDULER=0` locally — Flask's debug-reload would otherwise restart the schedule loop on every file save.

## Common issues

**Posts not auto-publishing?** Check the web service logs for `scheduler-loop` thread errors. Make sure `ENABLE_SCHEDULER=1` is set on the **web** service (not the cron). Confirm the plan is **Starter** or higher — Free-tier services sleep after 15 min idle and would skip every scheduled post.

**Cron returns 403 `invalid secret`?** The `CRON_SECRET` env var on the web service and on the cron must be the *exact* same string. Generate once, paste in both places.

**Cron returns 503 `CRON_SECRET not configured`?** You forgot to set `CRON_SECRET` on the **web** service.

**Dashboard "Start Applying" button times out?** The synchronous campaign takes ~3 minutes. Render's HTTP timeout is 5 minutes by default — should be fine. If it isn't, lower `count` to 50.

**Need to migrate from local?** SCP your existing `applied_jobs.json` and `external_applied_jobs.json` into the persistent disk via Render's Shell tab so you don't lose your dedup history:
```bash
# In Render → web service → Shell tab
cp /tmp/uploaded_applied_jobs.json /var/data/applied_jobs.json
```

## Why not Vercel?

Three blockers: Vercel's serverless functions have a hard 60s execution limit (your apply campaigns take 3 min), no persistent filesystem (state lives in `/tmp` and disappears on cold-start), and no long-running threads (the schedule loop dies after each HTTP request). Render's standard web service avoids all three.
